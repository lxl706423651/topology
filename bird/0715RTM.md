# Clean Linux 7.1.3 与 F/K1/K2c/K3c 全量 FIB 写入对比

日期：2026-07-15

## 1. 结论摘要

本轮 clean Linux 7.1.3 在 3083 规模下成功将 `6,131,994` 条 BIRD selected routes 写入 Linux main FIB，全量 writer wall time 为 `408.185s`，312/312 个 AS 固定代表节点通过 FIB/RIB 验证。

这个结果不能解释为“Linux 7.1.3 已经启用真正的 per-netns RTNL，但效果仍然很差”。源码核对表明：

1. Linux 7.1.3 已经把 IPv4 `RTM_NEWROUTE` 和 `RTM_DELROUTE` handler 标记为 `RTNL_FLAG_DOIT_PERNET`，并把锁操作移入 `inet_rtm_newroute()` / `inet_rtm_delroute()`。
2. 但本次构建配置为 `# CONFIG_DEBUG_NET_SMALL_RTNL is not set`。在该配置下，`rtnl_net_lock(net)` 仍直接退化为全局 `rtnl_lock()`。
3. 即使启用当前 7.1.3 的 `CONFIG_DEBUG_NET_SMALL_RTNL`，实现也会同时获取 global RTNL 和 per-netns mutex。Kconfig 明确说明这是迁移期的锁正确性检查机制，在 global RTNL 被最终移除前只会增加额外 mutex，并不会提供跨 namespace route-update 并行性。

因此，本轮 clean 7.1.3 测到的是“新版本内核上的标准 rtnetlink + global RTNL 路径”，而不是已经完成的官方 per-netns RTNL 性能。其 `408.185s` 与同样保留 global RTNL 的 K1 `402.388s` 几乎一致，也支持这一判断。

K2c/K3c 更快的根本原因不是单纯增加 worker，而是改变了内核提交粒度和同步路径：K2c 使用私有 bulk API、真正的 per-netns route lock 和 no-notify fast path；K3c 进一步对共享 nexthop/device/metric 的 route group 复用 cached `fib_info`。

## 2. 3083 规模全量写入结果

所有主要结果均对应 3083 output、约 2757 个 brdnode 和 `6,131,994` 条 initial full route ops。表中的 wall time 只比较 RIB-to-FIB writer，不包含 build、compose up、start-bird、load gate 和验证时间。

| 方法 | 内核与 route path | 有效 write workers | 提交粒度 | writer wall | 吞吐 | 相对 F-full |
|---|---|---:|---|---:|---:|---:|
| F-full | stock 6.8，`setns + ip -force -batch`，标准 `RTM_NEWROUTE` | 8 | 内核逐条 route message | `518.714s` | `11,822 ops/s` | `1.00x` |
| clean 7.1.3 | clean `7.1.3-upstream-pernet-rtnl`，标准 `RTM_NEWROUTE` | 8 | 内核逐条 route message | `408.185s` | `15,023 ops/s` | `1.27x` |
| K1 | 私有 bulk API + global RTNL | 1 | 256 ops/batch | `402.388s` | `15,239 ops/s` | `1.29x` |
| K2c | 私有 bulk API + per-NS route lock + no-notify + `fib_info_hash_mutex` | 8 | 2000 ops/batch | `71.162s` | `86,170 ops/s` | `7.29x` |
| K3c 6.8 | K2c + grouped cached `fib_info` | 16 | 16000 logical ops/batch，2000 ops/attr | `10.226s` | `599,667 ops/s` | `50.73x` |
| K3c 7.1.3 | 同一 7.1.3 代际上的 K3c-fibref-rtnlfix | 16 | 16000 logical ops/batch，2000 ops/attr | `7.061s` | `868,431 ops/s` | `73.46x` |

关键比例：

- clean 7.1.3 比旧 F-full 快 `1.27x`，但这不能归因于 per-netns RTNL，因为该功能未真正启用且当前迁移实现仍保留 global RTNL。
- clean 7.1.3 与 K1 只相差约 `1.4%`：`408.185s` 对 `402.388s`。两者仍由 global RTNL 串行化。
- 在同为 8 个 write workers 的条件下，K2c 比 clean 7.1.3 快 `5.74x`。
- 同一 7.1.3 代际下，K3c 比 clean 7.1.3 快 `57.81x`。
- K3c 7.1.3 比 K2c 再快 `10.08x`，说明解除 global RTNL 后，重复的 per-route `fib_create_info()` 又成为主要瓶颈。

这些 run 不是同一次 boot 上的严格微基准，绝对值可能受 cache、容器状态和脚本版本影响；但 route 数量相同、差距达到 `5.7x-57.8x`，足以支持路径级结论。论文中应报告多次重复实验的 median/p95，而不应把单次 wall time 写成无方差的普适常数。

## 3. 本轮 clean 7.1.3 的时间拆解

clean 7.1.3 的 F runner 使用 8 个 worker。每个 worker 对一个 brdnode 执行：

```text
birdc show route primary
  -> parse selected IPv4 routes
  -> generate ip route replace commands
  -> ip -4 -force -batch -
  -> standard RTM_NEWROUTE path
```

实测统计：

| 指标 | 数值 |
|---|---:|
| route ops | `6,131,994` |
| full writer wall | `408.185s` |
| effective workers | `8` |
| per-task dump time sum | `39.516s` |
| per-task dump avg / p95 / max | `0.014s / 0.026s / 0.190s` |
| per-task write time sum | `3173.293s` |
| per-task write avg / p95 / max | `1.151s / 1.297s / 1.540s` |
| maximum load1 | `15.507` |
| write failures | `0` |
| deterministic AS verification | `312/312` passed |

`39.516s` 是 2757 个容器 dump 时间的求和，不是并行 wall time。F 路径把 dump 与 write 放在同一个 8-worker task 中，因此没有独立的全局 dump-wall 字段。即使把全部 dump 成本忽略，数百秒级 wall time 仍由标准 route installation 主导。

## 4. 为什么源码已有 `RTNL_FLAG_DOIT_PERNET`，实际仍然是 global RTNL

### 4.1 7.1.3 handler 的表面变化

clean 7.1.3 在 `net/ipv4/fib_frontend.c` 中注册：

```text
RTM_NEWROUTE -> inet_rtm_newroute, RTNL_FLAG_DOIT_PERNET
RTM_DELROUTE -> inet_rtm_delroute, RTNL_FLAG_DOIT_PERNET
```

`RTNL_FLAG_DOIT_PERNET` 当前是 `RTNL_FLAG_DOIT_UNLOCKED` 的别名。其作用是让 rtnetlink dispatcher 不再在调用 handler 前自动获取 global RTNL。随后 IPv4 handler 自己调用：

```text
rtnl_net_lock(net)
  -> fib_table_insert() / fib_table_delete()
rtnl_net_unlock(net)
```

这一步完成了“把锁的所有权从 dispatcher 移到具体 handler”的代码迁移，但名称中的 `PERNET` 不等于 global RTNL 已经被移除。

### 4.2 本次构建没有启用 small-RTNL debug mode

本次 kernel build tree 的 `.config` 明确为：

```text
# CONFIG_DEBUG_NET_SMALL_RTNL is not set
```

在该配置下，`include/linux/rtnetlink.h` 中的实现是：

```text
rtnl_net_lock(net)   -> rtnl_lock()
rtnl_net_unlock(net) -> rtnl_unlock()
```

per-netns lock helper 只是兼容接口，实际同步域仍是全局 `rtnl_mutex`。VM 当前运行的 release 为 `7.1.3-upstream-pernet-rtnl`，与该 build tree 对应。

### 4.3 打开当前 debug config 也不会获得跨 NS 并发

7.1.3 的 `net/Kconfig.debug` 对 `CONFIG_DEBUG_NET_SMALL_RTNL` 的定义非常明确：迁移期间 `rtnl_net_lock()` 同时获取 global RTNL 和额外的 per-netns mutex，用于验证逐步缩小 RTNL 的锁依赖；只有转换完成并移除 global `rtnl_lock()` 后，rtnetlink 才能获得真正的 per-netns scalability。

因此，在当前 7.1.3 上简单打开该 config，预期结果是增加锁检查/lockdep 开销，而不是接近 K2c。它适合验证内核迁移正确性，不是当前阶段的性能开关。

## 5. clean 7.1.3 为什么慢于 K2c

clean 7.1.3 与 K2c 都使用 8 个有效 write workers，因此这个 `5.74x` 差距不能由 worker 数解释。主要差异有四项。

### 5.1 clean 路径仍被 global RTNL 串行化

8 个 F workers 可以并发准备命令和等待 ACK，但每条 standard route update 最终仍进入 global RTNL 临界区。增加 writer 只会增加等待者，不能让不同 namespace 的 FIB update 真正并行。

K2c 的私有 generic-netlink family 设置 `parallel_ops=true`，并只用目标 namespace 的 route mutex 串行化同一 NS 内的 writer。不同 NS 可以同时执行 FIB update。

### 5.2 `ip -batch` 不是内核 bulk route API

`ip -force -batch -` 省掉了反复启动 `ip` 进程和 shell 的成本，但 batch 中每一行仍被编码为独立的 `RTM_NEWROUTE` / `RTM_DELROUTE` message。内核仍要逐条完成 netlink 解析、配置构造、ACK/error 处理和 lock/unlock。

K2c 把紧凑的 route-op 数组作为一次私有 generic-netlink request 提交，单次进入内核后循环 apply 多条 route，从而减少 syscall、message parsing、ACK 和 lock handoff。

### 5.3 clean 保留完整 route notification 语义

标准 path 会维护正常的 rtnetlink multicast/notifier 可见性。K2c 的受控 fast path 使用 no-notify，避免 notifier 对 global RTNL 的依赖，也省掉数百万条 route notification 的构造和分发成本。

这是性能收益，也是语义 tradeoff：K2c 写入的 main FIB 可以正常 lookup 和转发，但 `ip monitor route` 等订阅者看不到 fast path 的逐条变化。

### 5.4 clean 每条 route 都走完整 FIB 构造路径

clean path 每条 route 都执行标准的 `rtm_to_fib_config() -> fib_table_insert() -> fib_create_info()`。K2c 虽然仍会为每条 route 调用 `fib_create_info()`，但已经通过 bulk submission、per-NS route lock 和 no-notify 移除了大量外围开销。

## 6. clean 7.1.3 为什么远慢于 K3c

K3c 包含 K2c 的全部优化，并增加了对 `fib_info` 的批内复用：

```text
group routes by nexthop/device/metric/protocol/table
  -> fib_create_info(base_cfg) once
  -> fib_table_insert_info(prefix_i, cached_fi) for each route
```

SeedEMU 中同一 router 的大量 selected routes 具有相同 nexthop、device、metric、protocol 和 table，通常只改变 prefix。standard route path 对每条 prefix 重复执行 `fib_create_info()`、hash lookup、引用维护和属性校验；K3c 把这些重复工作摊销到 route group。

7.1.3 K3c 的 full writer 具体为：

| 指标 | 数值 |
|---|---:|
| workers | `16` |
| logical batch / ops per attr | `16000 / 2000` |
| dump wall | `2.216s` |
| kernel/write wall | `4.843s` |
| total writer wall | `7.061s` |
| route ops | `6,131,994` |
| failures | `0` |

K3b 的历史实验已经表明：只把 logical batch 从 1024 增加到 16000、但仍逐条执行 `fib_create_info()`，性能基本不变。因此 K3c 的数量级收益主要来自 cached `fib_info`，不是单纯把 batch 调大。

## 7. 16 workers 是否造成了不公平比较

存在 worker 差异，但它不是主要原因。

1. clean 7.1.3 的有效 full-stage 并发是 `F_SHARDS=8`。命令行虽然还传了 `REAL_DUMP_WORKERS=16`，但 F solution 调用的是 `run_real_parallel(..., workers=f_shards)`；每个 worker 同时负责 dump 和 write，因此该参数没有把 clean F writer 变成 16 并发。
2. K3c 使用独立的 16-worker dump phase 和 16-worker bulk write phase。
3. clean 7.1.3 与同为 8 workers 的 K2c 相比仍慢 `5.74x`，已经排除了 worker 数这个变量。
4. 即使假设 clean 7.1.3 从 8 增加到 16 后获得不现实的完美线性加速，wall time 也只能从 `408.185s` 降到约 `204.1s`，仍比 K3c 的 `7.061s` 慢 `28.9x`。
5. K3c synthetic sweep 中，worker 从 8 增加到 16 只把 60M-route wall time 从 `30.567s` 降到 `18.098s`，收益约 `1.69x`，不是几十倍。
6. clean path 仍持有 global RTNL。过去 F writer sweep 已观察到并发超过拐点后出现 lock wait、D-state 和负优化，因此不能假设把 clean writer 直接调成 16 就一定更快。

严格量化 worker 影响仍需要在同一次 clean 7.1.3 boot、同一份已收敛 RIB 上做 `F_SHARDS=4/8/12/16` 重放，并监测 lock wait、CPU、load 和 D-state。本轮没有执行该 sweep，因此文档不把 `204.1s` 写成实测结果，只将其作为对 K3c 最有利的理论上界。

## 8. K3c 与 clean 7.1.3 的优劣

| 维度 | clean 7.1.3 standard route path | K3c fast path |
|---|---|---|
| 3083 full writer | `408.185s` | `7.061s` |
| 内核接口 | 标准 `RTM_NEWROUTE` / `RTM_DELROUTE` | 私有 `BIRD_RT_BULK` generic-netlink API |
| 同步 | 当前仍为 global RTNL | per-NS route lock + shared `fib_info` mutex |
| FIB 对象构造 | 每条 route 调用 `fib_create_info()` | 同组 route 复用 cached `fib_info` |
| route notifications | 保留标准 notifier/multicast | fast path no-notify |
| 工具兼容性 | 标准 `iproute2`、BIRD kernel protocol 和 route monitor 语义 | 需要专用 writer；`ip monitor route` 看不到 fast-path events |
| route 类型覆盖 | 使用 upstream 完整标准路径 | 当前聚焦 IPv4 main-table unicast；复杂类型回退/覆盖仍有限 |
| 数据面 | 真实 Linux main FIB，正常 packet forwarding | 同样写入真实 main FIB，`ping`/`iperf`/FIB lookup 正常 |
| 生命周期与安全 | upstream 回归、维护和安全更新成本最低 | 需要 fibref、netdevice/netns teardown 审计及专门回归测试 |
| 可维护性 | 升级到新内核无需维护私有 ABI | 每个目标内核版本需要移植、编译和验证 patch |
| 适用定位 | 通用 Linux networking 和完整语义 | 受控大规模网络仿真的高性能 FIB installation path |

clean 7.1.3 的优势是通用、标准、可维护和语义完整；K3c 的优势是在不放弃真实 Linux main FIB 和 packet forwarding 的前提下，把数百万 route installation 降到秒级。两者不是同一个设计点：clean path 优先保证通用 Linux 兼容性，K3c 优先满足受控 SeedEMU 场景中的规模性能。

## 9. 正确的论文表述

本轮结果不应写成：

```text
Linux 7.1.3 has per-netns RTNL, but it is still 57.8x slower than K3c.
```

更准确的表述是：

```text
Linux 7.1.3 contains the upstream migration scaffolding that moves IPv4
route handlers toward per-network-namespace RTNL scopes. However, in the
tested default configuration, rtnl_net_lock() still maps to the global RTNL;
even the current debug conversion mode retains the global lock. Consequently,
the standards-complete RTM_NEWROUTE path still installs 6.13M routes in 408s.
Our controlled K2c/K3c prototypes isolate the additional primitives required
for this workload: true cross-namespace route-update concurrency, bulk route
submission, and batched fib_info reuse. K3c reduces the same full-FIB write to
7.1s while preserving the Linux main-FIB forwarding semantics, at the cost of
a private API, restricted route coverage, and no per-route notifications.
```

这组结果支持两层结论：

1. upstream 正在朝更细粒度 RTNL 演进，说明 global RTNL scalability 是内核社区认可的问题；但 7.1.3 中的转换尚未完成，不能把 preparatory API 当成已经交付的 per-netns 并行实现。
2. 即使未来标准 route path 完成 per-netns RTNL，它仍需逐条 netlink 解析、notification 和 `fib_create_info()`。K2c/K3c 表明，面向大规模仿真还需要 bulk submission 与 batched FIB-object construction，per-netns locking 本身不是全部答案。

### 11.1 明确定性：当前标准 route-update 路径仍由 global RTNL 串行化

对本研究实际测试的 clean Linux 7.1.3，以及完整 backport 该系列的 Ubuntu 6.8，标准 IPv4 `RTM_NEWROUTE` / `RTM_DELROUTE` 路径仍然由 **global RTNL lock** 串行化，尚未获得跨 network namespace 的内核 FIB 写入并发。需要明确区分以下三个概念：

1. `RTNL_FLAG_DOIT_PERNET` 使 rtnetlink dispatcher 不再统一替 handler 获取 global RTNL，并把锁的获取位置移动到具体 IPv4 route handler；它本身不是一个独立的 per-NS 锁实现。
2. `rtnl_net_lock(net)` 提供了面向 namespace 的锁接口，但在当前迁移实现中，debug 配置会依次获取 global RTNL 和 per-netns mutex；普通配置则直接回退为 global `rtnl_lock()`。
3. 真正的 per-NS RTNL 并发要求从该调用路径中移除最外层 global RTNL，并完成对 notifier、nexthop、FIB rules、netdevice/netns teardown 及其他共享状态的同步审计。2025 年的 12-patch IPv4 FIB 系列没有包含这个最终步骤。

因此，以下表述是错误的：

```text
The upstream IPv4 patch already enables concurrent per-netns RTNL updates.
```

本文采用的准确表述是：

```text
The upstream series introduces per-netns RTNL migration infrastructure and
converts the IPv4 route handlers to the new locking interface. However, the
tested standard RTM_NEWROUTE/RTM_DELROUTE path still retains the global RTNL
serialization boundary and therefore does not execute FIB updates concurrently
across network namespaces.
```

这一定性同时得到源码语义和动态 trace 支持：debug 构建确实观测到 40,000 次 `rtnl_net_lock()`，但 `fib_table_insert()` 最大并发仍为 `1`；普通构建的最大并发同样为 `1`。因此，即使将完整系列 backport 到 6.8 并自行编译，也只会复现迁移期语义，不会自动得到真正的 per-NS RTNL scalability。该结论仅表示“这套 upstream 系列本身不足以解决问题”，不表示内核层面无法继续实现；K2c/K3c 已经证明，在明确约束 route 类型和 notification 语义后，可以通过额外内核设计实现跨 namespace 并发。

### 11.2 版本边界核查：直接相关的首个正式版本是 Linux 6.15

早期 `v6.13-rc7` Kconfig 只能说明 per-netns RTNL 前置基础设施的初始设计，不能单独证明 2025-02-28 IPv4 FIB 系列合入后的最终行为。为排除时间顺序造成的误判，本研究进一步核查了该系列前后的主线源码：

| 主线版本 | IPv4 handler 中的 `rtnl_net_lock(net)` | `RTNL_FLAG_DOIT_PERNET` | 结论 |
|---|---|---|---|
| Linux 6.14 | 无 | 无 | 12-patch IPv4 FIB 系列尚未进入该正式版本 |
| Linux 6.15 | 有 | 有 | 该系列已进入主线；这是直接相关的首个正式版本 |

Linux 6.15 发布于 2025-05-25，晚于 2025-02-28 的 v3 patch series。最终提交 `1dd2af7963e9` 是 `v6.15` 的祖先提交，而不是 `v6.14` 的组成部分。更重要的是，补丁合入后的 `v6.15` 仍保留以下明确语义：

```text
CONFIG_DEBUG_NET_SMALL_RTNL=y:
    rtnl_net_lock(net) -> rtnl_lock() -> __rtnl_net_lock(net)

CONFIG_DEBUG_NET_SMALL_RTNL=n:
    rtnl_net_lock(net) -> rtnl_lock()
```

`v6.15/net/Kconfig.debug` 也仍然说明：迁移期间 `rtnl_net_lock()` 会同时获取 global RTNL 和额外的 per-netns mutex，只有后续从 helper 中移除 global `rtnl_lock()` 后才会获得 per-netns scalability。因此，`v6.13-rc7` 的引用虽然较早，但内容并未被 2025-02-28 系列推翻；使用直接包含该系列的 Linux 6.15 源码复核后，结论仍然相同。

这一版本核查还解释了 `RTNL_FLAG_DOIT_PERNET` 容易引起的误读。在 Linux 6.15 中，该标志仍是 `RTNL_FLAG_DOIT_UNLOCKED` 的别名：它让 dispatcher 不在 handler 外层自动获取 RTNL，但随后 `inet_rtm_newroute()` / `inet_rtm_delroute()` 调用的 `rtnl_net_lock(net)` 仍会获取 global RTNL。换言之，handler 的锁所有权和迁移边界已经调整，但实际互斥域尚未缩小到单个 namespace。

### 11.3 最新主线复核：截至 Linux 7.2-rc3 迁移仍未完成

Linux `v6.19-rc8` 与 `v7.2-rc3` 的 `CONFIG_DEBUG_NET_SMALL_RTNL` 帮助文本仍明确说明：`rtnl_net_lock()` 在迁移期间同时获取 global RTNL 和一个 per-netns mutex；这个额外 mutex 目前只用于逐步转换和锁依赖验证，并会增加操作开销。只有转换完成并从该 helper 中移除 global `rtnl_lock()` 后，rtnetlink 才会获得真正的 per-netns scalability。两个相隔多个开发周期的版本保留相同说明，证明该结论不是来自已经过时的 `v6.13-rc7` 文档。

`v7.2-rc3` 的实际实现也与帮助文本一致：启用 `CONFIG_DEBUG_NET_SMALL_RTNL` 时，`rtnl_net_lock(net)` 先调用 `rtnl_lock()`，再调用 `__rtnl_net_lock(net)`；未启用该配置时，inline fallback 只调用 `rtnl_lock()`。因此，当前状态应准确表述为：

1. `rtnl_net_lock()` **接口已经实现**，每个 network namespace 中的辅助 mutex 也已经存在。
2. `rtnl_net_lock()` **尚未实现仅依赖 per-netns mutex 的锁语义**；它仍保留 global RTNL 串行化边界。
3. 标准 `RTM_NEWROUTE` / `RTM_DELROUTE` 即使迁移到该接口，也不能仅凭这次 API 替换在不同 namespace 中并发执行 FIB 临界区。

所以，本文所说的“`rtnl_net_lock()` 尚未实现”特指 **真正的 per-NS RTNL 并发与可扩展性尚未实现**，并不是说内核中不存在该函数。直到本研究核查的最新版本 `v7.2-rc3`，upstream 仍处于“global RTNL + 迁移期 per-netns mutex”的过渡阶段。

RTNL contention 是 Linux networking control path 中长期已知的 scalability limitation。Westphal 的系统性分析指出，rtnetlink 的 link、address、route、qdisc 和 traffic-classifier 等主要配置路径广泛共享单个 RTNL mutex，使添加 FIB entry 与读取无关网络配置等本可独立的 operation 也相互阻塞；部分 callback 还可能因内存分配或等待 RCU grace period 长时间持锁，因此 RTNL 被称为 networking stack 的 ``big kernel lock''，而解除该锁又必须先逐项修复既有 handler 对 RTNL consistency guarantee 的依赖~\cite{westphal2017rtnl}。Linux networking documentation 同样明确记载，历史上所有 networking control operation 都由单一 global \code{rtnl\_lock} 保护，当前演进方向是逐步迁移到 per-network-namespace lock，并以 netdev instance lock 保护更多 per-device property 和 control operation~\cite{linux_netdev_locking}。Iwashima 的提交 \code{76aed95319da} 引入了 per-netns mutex 以及 \code{rtnl\_net\_lock(net)} / \code{rtnl\_net\_unlock(net)} migration interface，该基座首次进入正式主线 Linux 6.13；其提交说明明确把迁移过程定义为替换 800 余处 \code{rtnl\_lock()}，并规定在转换完成前 \code{rtnl\_net\_lock(net)} 仍获取 global RTNL，只有最终从 helper 中移除 global \code{rtnl\_lock()} 才能获得 per-netns scalability~\cite{iwashima2024pernetns}。随后 2025 年 IPv4 FIB v3 patch series 先将两个 \code{fib\_info} hash table namespacify，再把 \code{RTM\_NEWROUTE} 和 \code{RTM\_DELROUTE} handler 的锁获取移入 \code{rtnl\_net\_lock(net)}，并以 \code{RTNL\_FLAG\_DOIT\_PERNET} 避免 dispatcher 在 handler 外层重复加锁；最终提交 \code{1dd2af7963e9} 首次进入正式主线 Linux 6.15，Linux 6.14 尚不包含这一 IPv4 handler conversion~\cite{iwashima2025fib_pernetns,torvalds2025linux615}。但是，这次转换只调整了锁的获取位置、namespaced shared state 和迁移接口，尚未消除 global serialization boundary：在 Linux 6.15 及本文核查的后续主线实现中，普通 build 的 inline \code{rtnl\_net\_lock(net)} 仍直接映射到 global \code{rtnl\_lock()}，\code{CONFIG\_DEBUG\_NET\_SMALL\_RTNL} conversion mode 则先获取 global RTNL、再获取 per-namespace mutex。因此，这些配置下的标准 IPv4 FIB update 仍会跨 namespace 串行执行；准确结论是 Linux 6.13 建立了 per-netns RTNL 的迁移基座，Linux 6.15 将 IPv4 route-update path 接入该基座，但 global RTNL 尚未移除，真正的 per-network-namespace route-update concurrency 尚未由该上游系列实现，这也与本文动态 trace 中 \code{max\_concurrent\_worker\_fib\_inserts=1} 的结果一致。
